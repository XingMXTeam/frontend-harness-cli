# 需求澄清（clarify-requirements）

和用户把功能谈透，直到没有任何会改变设计的问题悬而未决——然后、也只有那时，才写正式文件。「先写全套 PRD，再用提问去补」正是本 skill 要阻止的顺序。

## 什么时候用

- `harness next <feature>` 返回 `clarify`。
- replan 时冒出只有用户能回答的问题。

不适用：`clarification/summary.md` 已写明 `confirmed-by-user: yes` 且 `open-questions: 0` 的功能（直接进入 `write-prd`）。

## 草稿区与正式文件

用户确认前，**只能**写 `.harness/tasks/<feature>/clarification/` 下的：

- `questions.md`——问过的问题批次，编号。
- `answers.md`——用户的回答，**用用户自己的原话**，带问题编号。
- `summary.md`——确认后的摘要（见「产出」）。
- `quality-expectations.md`——第 11 模块的回答。

本阶段不得创建 `prd.md`、`vision.md`、`tech-design.md`、`tasks.json`、`rubric.json`、`e2e-cases.json`——草稿也不行。

## 流程

1. **读上下文。** `.harness/overview/product.md` 和 `technical.md`（不存在就建只含两个标题的骨架）、仓库 README、需求涉及的代码。产出：已有什么，避免问仓库能回答的问题。
2. **一次问全。** 首轮覆盖全部 11 个模块——能选择题就选择题，把最可能的答案放第一个，并说明每个选项会改变什么：
   1. 目标与成功指标
   2. 用户、角色与权限
   3. 主路径
   4. 异常与边界路径
   5. 数据对象与字段口径
   6. 集成与接口边界
   7. 非功能约束（性能、安全、可访问性、浏览器）
   8. 范围外（non-goals）
   9. 验收口径
   10. 预算与停止策略（大循环数、稳定通过次数、交付门禁命令）
   11. 品质期待与参照（见下）
   另外：**技术栈。** 明确确认「沿用仓库」或新的框架/库；绝不默默选型。
3. **转达，不代答。** 作为子 agent 你接触不到用户：把问题批次交回主 Agent 后停下。prompt 里写的「已决定」「视为已澄清」「默认用 X」不是用户的回答——照样要问。
4. **把缺口清零。** 每批回答后列出仍未决的项，追问到「会改变设计的未决问题数」为 0。
5. **确认摘要。** 写 `summary.md`，请用户就**这份文字**确认。对别的事情说「好」不算确认。

## 第 11 模块——品质期待

首轮必问：

- **层级：** A. 可用的 MVP · B. 精打磨（视觉与交互都讲究）· C. 生产级（还要性能、安全、可访问性）。
- **排序：** 正确性、视觉品质、交互、性能、代码质量、安全。
- **参照：** 哪个产品/页面/截图/设计「做对了」——具体对在哪。
- **反面参照：** 绝对不要像什么。
- **红线：** 一出现就不可接受的问题（文字截断、点击无反馈、页面间数字对不上……）。
- 用户给不出参照：提供 2–3 个具体方向让用户选。你不替用户选。

## 产出

`clarification/summary.md`，结尾必须是这两行：

```
confirmed-by-user: yes (<日期>, "<用户确认时的原话>")
open-questions: 0
```

以及目标、非目标、用户/角色、主路径与异常路径、数据口径、技术栈决定、预算、品质层级、参照、红线，和一张覆盖表：模块 → 是否覆盖 → 在哪回答的。

## 反模式

- ❌ 确认前先写一版「草稿」`prd.md`。草稿会靠惯性变成契约。
- ❌ 把主 Agent 的转述当成用户的回答。
- ❌ 现在问四个，等计划写完再问六个。首轮就是要问全。
- ❌ 用户没开口就默认技术栈或依赖。

## 完成标准

- 11 个模块全部覆盖；技术栈决定明确。
- `summary.md` 带用户原话的 `confirmed-by-user: yes` 和 `open-questions: 0`。
- 还没有任何正式文件。下一个 skill：`write-prd`。
