# 交付前检查清单（ship-checklist）

「做完了」是一个断言，断言需要证据。在你脑子里、在你机器上能过类型检查的代码，不叫做完。这个 skill 是「我写了」和「它完成了」之间的最后一道门：每一项要么实际跑过、读过，要么明确标注未跑——并写明原因。

## 什么时候用

- 宣布任何任务、功能或修复完成之前。
- 开 PR 或合并 PR 之前。
- 长会话之后，改动清单已经超出你的记忆范围时。
- 把工作交给另一个人或另一个 Agent 评审时。

## 流程

1. **类型与 lint。** 完整跑项目的类型检查和 lint 命令（不只跑改动文件，除非项目把门限定成那样）。产出：两者都干净退出，或失败清单。
2. **存在的测试，真的跑。** 跑测试套件或项目定义的子集；记录真实计数（通过 / 失败 / 跳过）。产出：这次运行的数字——永远不要用记忆或上一次运行的数字。
3. **构建。** 按 CI 的方式跑生产构建。产出：构建结果；如果 CI 是构建制，开发服务器冒烟测试不能替代。
4. **审 diff。** 以评审者的眼光把自己的完整 diff 读一遍。产出：残留的调试输出、注释掉的代码、无关改动、误改的文件，全部找出并清除。
5. **爆炸半径清单。** 枚举这次改动可能影响什么：动过的共享组件、变更的公共 API、消费了被改代码的其他页面或功能。产出：一份书面清单，每条要么实际走过、要么论证安全、要么标为风险。
6. **验收标准，逐条对。** 把最初的计划或需求逐项走一遍，标注达成 / 未达成 / 经需求方同意后砍掉。产出：没有一条标准停留在「大概做完了」。
7. **诚实的总结。** 写交付说明：交付了什么、带数字的检查结果、什么**没有**验证及原因、已知风险。产出：一份评审者不用重跑任何东西来核查你的诚实度、只需核查你的工作的总结。

## 反模式

- ❌ 报告「测试通过」，而那次运行发生在你最后三轮编辑之前。代码一变，证据就过期。
- ❌ 把类型检查绿当作构建绿：打包、资源处理、环境变量只会在真正的构建里失败。
- ❌ 悄悄缩小「完成」的定义——「就这一次」跳过慢套件，总结里却写得像跑过一样。
- ❌ 把未验证项埋在散文里（「生产上应该没问题」），而不是列在「未验证」之下让评审者自己权衡。

## 完成判据

- 类型检查、lint、测试、构建都在最后一次编辑之后跑过，结果（含计数）已记录。
- 完整 diff 已自审；无残渣、无关改动已清除。
- 爆炸半径已写下，每条都有处置结论。
- 每条验收标准都标为达成、未达成或已砍——任何未验证项都在总结里被明确点名。
