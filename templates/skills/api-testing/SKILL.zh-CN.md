# 接口测试（api-testing）

从外部用真实调用检查契约。开发者的报告不是证据；你自己的请求才是。

## 输入

- `tech-design.md` 的「API / 接口契约」一节。
- 依赖该 API 的 `prd.md` 需求和 `e2e-cases.json` 用例。
- 按 `tech-design.md` 启动的应用或 API。

## 流程

1. 按契约列用例：成功、每种已声明的错误、边界（空、最大长度、分页边缘）、无权限、格式错误的输入。
2. 每个用例都发真实请求（`curl`、`fetch`、Playwright 的 `request` 上下文）。mock 掉的传输层不是证据。
3. 每个用例记录：方法 + 路径、请求体/参数、期望状态码与结构、实际状态码与响应体（截短）、结论。
4. 日志存到 `.harness/tasks/<feature>/evaluation/api-<cycle>.md`，并在相关 judge 条目的 `artifacts` 里引用。
5. 契约不符是带严重级别的发现；契约缺失（方案没说错误长什么样）是一条改进建议（`add-verification`）。

## 规则

- 独立：不用开发者的脚本当证明。
- 不为让用例通过而修改产品代码或数据夹具。
- API 用例只证明 API——绝不证明浏览器旅程。

## 完成标准

- 每个契约用例都已执行，有请求/响应记录和结论；日志被它所支撑的 judge 证据引用。
