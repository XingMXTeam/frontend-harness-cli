# 国际化提取与校验（i18n-extract）

国际化是悄悄坏的：一句硬编码文案以一种语言上线，一个组件调用了从没加进资源文件的 key，没人发现，直到用户截图发出来。这个 skill 两半一起做——提取和完整性校验——只做一半，故障模式就还在。

## 什么时候用

- 给代码库或某个功能区加 i18n 支持。
- 发布前、或把文案交给译者之前，审计一个功能。
- Bug 报告里出现原始 key（「home.title」）或界面上的未翻译文本。
- 一次把组件在页面或命名空间之间搬了家的重构之后。

## 流程

1. **先定约定。** 从代码库确认：资源文件的组织方式、key 命名模式（如 `namespace.section.key`）、代码里调用翻译的方式。产出：写下来的约定；如果还没有，先提议并取得一致再动文件。
2. **扫硬编码字符串。** 在目标代码里搜用户可见的字面量：JSX 文本、按钮标签、placeholder、aria-label、toast 和错误信息。产出：file:line 命中清单，排除不可见字符串（类名、测试 ID、日志信息——按项目约定）。
3. **用稳定 key 提取。** 把每条文案放进资源文件，key 要能说清它的位置和含义，再把字面量替换成翻译调用。产出：资源条目与调用点一一对应。
4. **双向校验完整性。** 代码里每个翻译调用，检查 key 在资源文件中存在；资源文件里每个 key，标注有没有被调用。产出：两份清单——缺失 key（必须为零）和未使用 key（报告，不要自动删）。
5. **每个语言都查，不只默认语言。** 对每个已发布的语言文件重复存在性检查。产出：按语言的缺失 key 计数；一个 key 在某个语言里缺失是缺陷，不是 TODO。
6. **实际跑一遍界面。** 条件允许时，用非默认语言加载受影响的页面，看有没有原始 key 或回退文本。产出：已查的页面，或一条明确的「未运行」备注。

## 反模式

- ❌ 拿英文句子当 key（「Click here to continue」）。第一次改文案就让所有调用点变孤儿；key 命名的是含义和位置，永远不是措辞。
- ❌ 拼凑翻译片段（「You have 」 + n + 「 items」）。各语言语序不同；用带占位符的参数化消息。
- ❌ 只提取可见的顺利路径，把错误 toast、空状态、校验信息留成硬编码——那些恰恰是用户会截图的字符串。
- ❌ 只更新默认语言就宣布完成，其他语言静默缺新 key、运行时回退。

## 完成判据

- 审计范围内零硬编码用户可见字符串残留。
- 每个翻译调用在每个已发布语言里都能解析到存在的 key（缺失计数按语言报告，且为零）。
- 未使用的 key 列在报告里，没有被静默删除。
- Key 一致遵循项目的命名空间约定。
