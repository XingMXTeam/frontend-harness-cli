# 先规划，后写码（plan-before-code）

不要从一句模糊的话开始。写代码之前，先把「做到什么样才算完成」谈清楚，写成功能点（FP）清单——第三方能逐条验证的那种。

## 什么时候用

- 用户要一个新功能、新页面、新流程或新界面。
- 需求只有一句话，藏着一堆真实决策（「加个设置页」「让结账更快点」）。
- 改动牵涉多个文件、组件或数据源。
- 你发现自己正要动手写代码，而验收标准只存在于自己脑子里。

不适用于：一行能改完的修复、纯改名、以及用户已经给全了可测规格的改动。

## 流程

1. **一句话复述目标。** 谁做什么、做完之后对他有什么不同。产出：一句用户能点头或纠正的话。
2. **列出未知项。** 扫一遍需求里缺的决策：空状态、错误处理、权限、数据来源、边界情况。产出：编号的问题清单，或明确写下的假设。
3. **解决或假设。** 会改变设计的未知项去问；其余的写成假设记录下来。产出：每个未知项要么有了答案，要么作为假设写在计划旁边。
4. **拆成功能点。** 把功能拆成 FP，每条用 `输入 -> 动作 -> 校验 -> 结果` 的格式。例：「FP-1：用户输入非空标题 -> 点击添加 -> 标题去空格并校验 -> 条目出现在列表里且输入框清空。」产出：编号 FP 清单，每条都能独立测试。
5. **写明非目标。** 这次改动明确不做什么。产出：一份明确的范围外清单（至少一条）。
6. **定义「完成」。** 每个 FP 分别说清怎么验：一个测试、一个手动步骤、一个可见结果。产出：每个 FP 一条完成判据，而不是一句笼统的「能跑就行」。
7. **动手前先确认。** 有承重假设时把计划给用户看，然后停住。产出：一份已确认的计划，存到团队放计划的地方（文件、issue 或 PR 描述）。

## 反模式

- ❌ 从「做个首页」直接开写——六小时后用户发现你做错了六小时。
- ❌ 悄悄发明缺失的需求：规格没提，就自己挑个错误码、空状态文案或权限规则，而不是去问或记为假设。
- ❌ 把 FP 写成实现任务（「建组件 X」「加 hook Y」）。任务描述的是你的活；FP 必须描述用户或测试能观察到的行为。
- ❌ 把计划当仪式：计划写得漂漂亮亮，然后写的是另一套东西，还从不拿结果回来对。

## 完成判据

- 有一份书面计划，包含：目标句、输入 -> 动作 -> 校验 -> 结果格式的 FP 清单、假设、非目标、每个 FP 一条可检验的完成判据。
- 计划存在之前没有写任何代码。
- 每个 FP 都能由没写这段代码的人回答「过 / 不过」。
