# 编写 PRD（write-prd）

把确认过的摘要变成产品契约：问题是什么、谁有这个问题、功能必须做什么、不做什么——用测试者能核对的话写。

## 门禁

- `clarification/summary.md` 存在，且有 `confirmed-by-user: yes` 和 `open-questions: 0`。否则停下，回到 `clarify-requirements`。
- 读 `.harness/overview/product.md` 和 `technical.md`，核对范围与既有能力、边界是否一致。

## `prd.md` 结构

1. **问题**——谁的问题，用他们的说法，为什么是现在。
2. **用户与场景**——角色和他们所处的情境。
3. **用户故事**——「作为……我想要……以便……」。
4. **需求**——编号 `REQ-1`、`REQ-2`……每条一句可测的话。这些 id 原样成为 `rubric.json` 的 requirements。
5. **非功能需求**——可度量（时间、体量、浏览器、可访问性等级）。
6. **成功画像（What good looks like）**——每个关键页面、每个核心交互 2–3 句，描述用户认可的目标状态（见下）。
7. **范围外**——明确不做的。
8. **成功指标**——怎么知道它成功了。
9. **概览增量**——新的能力域或边界变化，每条一行，留给 `sync-overview` 之后处理（或写「无」）。

## 「成功画像」

写到开发者和评估者脑中会浮现同一个画面。

- 差：「列表页要简洁现代。」
- 好：「列表一行一条通知，最新在上；未读行标题加粗并带圆点；行间距 12–16px；空列表显示一句话和一个『刷新』按钮。」

本节是摘要；完整锚点在 `vision.md`。两者保持一致。

## 规则

- 一个 PRD 只覆盖一个功能。不写实现细节（框架、文件名）——那是技术方案的事。
- 每条需求都能被非作者核对。
- 沿用 `answers.md` 里用户的用词，不改名。
- 不写 TODO / TBD。还有未决问题，说明你还不该进入本 skill。
- 不写 `.harness/overview/`——增量列在第 9 节。

## 完成标准

- `prd.md` 九节齐全；需求编号为 `REQ-n`。
- 每条需求可追溯到摘要；每个非目标都写明。
- 下一个 skill：`write-quality-vision`。
