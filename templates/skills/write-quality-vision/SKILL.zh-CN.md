# 编写品质愿景（write-quality-vision）

`vision.md` 是「用户期望它给人什么感觉」与「评估者打什么分」之间的桥。rubric 里的 judge 条目必须引用本文件中的锚点；不引用的会被内核拒绝。

## 门禁

- `prd.md` 已存在，`clarification/summary.md` 已确认。
- 读 `clarification/quality-expectations.md` 和 PRD 的「成功画像」。愿景里的一切都来自用户的回答——你不发明品味。

## 锚点语法（内核解析）

一行一个锚点，可放文件任意位置：

```
REF-1: <正面参照——好在哪、在哪能看到>
ANTI-1: <反面参照——要避免什么、为什么>
RL-1: <红线——绝不可接受> (check: screenshot|dom|command)
```

`clarify-done` 强制的最低数量：REF ≥ 1、ANTI ≥ 1、RL ≥ 2，且每条 RL 声明检查方式。以 `screenshot` 检查的红线，其 judge 条目必须引用一张真实 PNG。

## 结构

```markdown
# Quality vision — <feature>

## 1. 品质定位
层级：MVP | 精打磨 | 生产级
优先级：正确性 > 交互 > 视觉 > 性能 > …
基调：<一句话，如「密集而安静的工作工具，信息优先」>

## 2. 参照
REF-1: <来源> — 值得学：<具体特征> — 适用：L3/L4
ANTI-1: <来源> — 避免：<具体特征> — 适用：L3/L4

## 3. 设计意图
- 视觉：<关键词；色板方向或 token；字体方向>
- 密度：紧凑 | 均衡 | 留白 | 仪表盘
- 交互范式：直接操作 | 向导 | 表单提交 | …
- 关键页面：
  | 页面 | 用户目标 | 目标状态 | 锚点 |

## 4. 红线
RL-1: <绝不可接受> (check: screenshot)
RL-2: <绝不可接受> (check: command)

## 5. 与 rubric 的映射
- 设计意图 -> L3 条目；交互范式 -> L4 条目
- RL-n -> pitfall 条目（或引用 RL-n 的 essential judge 条目）
- REF-n -> 每次全量评估都做对比
```

## 规则

1. **具象胜过形容词。**「卡片间距 12–16px，次要文字用 neutral-600 token」——而不是「要好看」。
2. **每个参照都有注解。** 只有链接、没有「好在哪」的不算锚点。
3. **每条红线都可检测**——截图、DOM 或命令。「要快」不是红线；「任何点击 100ms 内有可见反馈」是。
4. **你提议的方向**（用户没有参照时）只有在澄清阶段被用户选中后才能写进来。
5. **没有 UI？** 保留第 1、4、5 节，写 API 品质锚点（错误格式一致、提示可操作），并写 `ui-vision: N/A — <理由>`。

## 完成标准

- REF ≥ 1、ANTI ≥ 1、RL ≥ 2 且带 `(check: …)`；每个关键页面都有目标状态。
- 文件里没有任何一条找不到用户回答作为来源。
- 下一个 skill：`write-tech-design`。
