# 按设计系统做组件（component-from-design）

生成的 UI 会漂移：AI 随手抓一个看起来接近的 hex 值、一个感觉差不多的间距、一个凭记忆的字号。每个选择都「差不多」，加起来就是一套跟任何设计稿都对不上的 UI。这个 skill 让设计系统成为视觉取值的唯一来源。

## 什么时候用

- 按设计规格、设计稿或截图新建组件。
- 把现有组件重做样式以对齐设计系统。
- 评审一遍下来到处「差一点点」的生成 UI。
- 在有设计 token 的仓库里干活（CSS 变量、theme 对象、token 包）——尤其这种时候。

## 流程

1. **先读 token 源。** 打开项目的 token 定义（变量文件、theme、设计 token 包），列出这个组件需要的 token：颜色、间距阶梯、字号、圆角、阴影。产出：一份 token 短清单；需要的取值没有 token，现在就标记出来，不要做到一半现编。
2. **把规格值映射到 token。** 写样式之前，把规格里的每个视觉值翻译成 token 名。产出：形如「卡片内边距 16px -> var(--spacing-4)」的映射表。映射不上的值是给设计师或用户的问题，不是硬编码的邀请函。
3. **先复用再新建。** 在组件库里找有没有现成组件或变体能覆盖这个需求。产出：记录复用决策（复用了 X / 新建因为 Y）。
4. **样式只用 token。** 新代码里每个颜色、间距、字号都引用 token 或现成组件的 API。产出：对新样式搜裸 hex/px 值，除允许的例外（如设计系统允许的 1px 边框）外一无所获的代码。
5. **对着规格自查。** 把结果和设计稿比：工具允许就截屏，否则逐元素走查结构（顺序、层级、状态）。产出：一份核过的元素与状态清单（默认、悬停、禁用、空、错误），不一致的已修复或已上报。
6. **报告缺口。** 列出规格里没有 token 的值及其解决方式（提议新 token、经批准用了最接近的 token、或留作标记的例外）。产出：没有任何一处静默即兴发挥。

## 反模式

- ❌ 凭眼估个颜色、把记住的 hex 敲进去——设计系统的主色不是你训练数据里的那个。
- ❌ 因为「16px 和 token 的 15px 看不出区别」就用一次性像素值——十处看不出的偏差，正是设计漂移的发生方式。
- ❌ 组件库明明有现成的按钮/卡片/弹窗，还从头再写一个，因为写比读它的 API 感觉更快。
- ❌ 只查默认状态：规格里的悬停、禁用、空状态，恰恰是 token 纪律最先崩的地方。

## 完成判据

- 新样式里没有硬编码的颜色、间距、字号值；一切都解析到 token 或共享组件。
- 组件已在全部状态下与规格比对过，用截屏或结构化走查。
- 每个 token 缺口都连同解决方式报告了；没有一处被静默即兴处理。
