# 状态 Schema 先行（state-schema-first）

状态 bug 是发现得太晚的设计 bug：两个组件各存一份同一事实的副本，一个持久化 key 和另一个功能撞了车，没人说得清初始值应该是什么。先写 schema，把这些变成在纸面上一次性做完的决策，而不是在生产环境里发现的 bug。

## 什么时候用

- 新功能需要客户端状态、store 或缓存。
- 数据会被持久化（localStorage、sessionStorage、IndexedDB、cookie）。
- 服务端数据和本地编辑要共存（草稿、乐观更新、离线队列）。
- 调试时发现多个组件对同一个值各执一词。

## 流程

1. **列事实。** 把功能需要的每一份状态枚举出来，一行一个事实。产出：一份事实清单，此时还不选类型。
2. **写 schema。** 每个事实定义：字段名、类型、默认/初始值、是否允许缺失。产出：一份 schema（TypeScript 类型、JSON schema 或表格——用项目的惯例形态），评审者不用打开组件代码就能读。
3. **指定唯一事实源。** 每个事实指名它唯一的归属：服务端、store、URL、表单状态，或由 X 派生。有两个归属的事实现在就重新设计，不要留到以后去同步。产出：归属一列，每行恰好一条。
4. **区分服务端状态与客户端状态。** 标明哪些事实是服务端数据的缓存副本、哪些只存在于本地；两者的生命周期和失效规则不同。产出：这个区分在 schema 里显式写明。
5. **给持久化 key 加命名空间。** 每个存储 key 遵循 `{app}.{feature}.{field}` 这样的模式；形状可能演化的话带上版本段。产出：key 清单，并已对着代码库已有 key 做过撞车检查。
6. **定义状态迁移。** 列清谁能改每个事实、何时改（动作/事件，而不是「任何地方」）。产出：足够的可追溯性，让「它怎么变成这个值的」能从代码里回答。
7. **然后才写代码。** 组件消费 schema，不许随手扩它。新事实先走一遍第 1–6 步。产出：实现与 schema 逐字段对应。

## 反模式

- ❌ 把同一事实散在组件状态、全局 store 和 localStorage 里，再加一个 effect 去「保持同步」——同步代码就是在承认 schema 从来没定过。
- ❌ 用 `"settings"`、`"draft"` 这种裸 key 持久化，下一个功能（或明年的同一个功能）迟早撞上。
- ❌ 让形状静默演化：在一处加个字段、其他地方到处防御性读取，存量值从不迁移也不加版本。
- ❌ 把服务端数据建成模成本地状态，手搓项目数据层早就处理好的重取、过期和错误标志。

## 完成判据

- 有一份书面 schema，覆盖功能用到的每个事实，每个都有类型、默认值和唯一归属。
- 所有持久化 key 都有命名空间且查过撞车。
- 没有事实有两个事实源；派生值都标明是派生。
- 实现与 schema 相符——靠把两者对着读来验证，不靠记忆。
